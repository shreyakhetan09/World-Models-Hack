# RescueSim: Build Prompts

An AI rescue agent that drives itself through disasters generated by a world model. It **sees and hears**: it combines camera frames with spatial audio (cries for help, tapping, gas hiss, structural creaking) to make difficult calls on its own. It **imagines possible futures before taking risky moves** and **guides a human survivor out by voice in real time**. The cloud model also teaches a **small onboard model that keeps working with no network**. A **side-by-side comparison** shows why it beats conventional agents that are trained on a few fixed maps, rely on vision only, and only react to what's in front of them.

Stack: **Reactor** (Lingbot-World-2, real-time world model, video) + **Google AI Studio models** (Gemini Robotics ER 2 for vision + audio reasoning, Gemini TTS for survivor voices, Gemini Live for the voice guide, Gemini Flash + image model for scenarios) + Python FastAPI backend + Next.js frontend.

## Architecture

```
                         ┌──────────────────────────── SCENARIO ─────────────────────────────┐
                         │ world_prompt + reference image + traps + AUDIO SOURCES on the map   │
                         │ (presets, or generated by Gemini Flash + image model + Gemini TTS)  │
                         └───────────────┬──────────────────────────────────┬─────────────────┘
                                         │                                  │
                 ┌───────────────────────▼─────────┐            ┌───────────▼───────────────────┐
                 │ Reactor world model (VIDEO only) │            │ Audio scene engine (ours)      │
                 │ main session + imagination forks │            │ sources at map positions,      │
                 │ prompt changes: director events, │            │ start/stop times, muffling     │
                 │ traps, "reveal" when agent        │            │ (behind walls/under rubble)    │
                 │ reaches a sound source            │            └──────┬───────────────┬────────┘
                 └───────────────┬──────────────────┘                   │               │
                                 │ frames (2 fps)            mono clip  │               │ same sources,
                                 │                           + bearing/ │               │ spatialized for
                                 │                    distance from the │               │ the room's
                                 │                   simulated mic array│               │ speakers (Web Audio)
                                 ▼                                      ▼               ▼
┌────────────────────────────────────────────────────────────────────────────┐   ┌────────────────────┐
│ BRAIN (cloud): Gemini Robotics ER 2                                         │   │ Frontend           │
│  in:  frame + audio clip (only when a sound is detected) + heard-bearings   │   │ video + HUD +      │
│       + mission state (pose, survivors, hazards, heard sources) + playbook  │──▶│ AUDIO RADAR +      │
│  out: JSON decision {action, survivors, hazards, heard[], reason, priority} │   │ imagination tiles  │
│  at decision points → IMAGINATION: fork Reactor per option, score futures   │   │ + compare view     │
└──────────────────────────────┬─────────────────────────────────────────────┘   └────────────────────┘
                               ▼
            SAFETY LAYER (deterministic rules, cannot be overridden by any model):
            severity-3 visual hazard ahead → back off · gas hiss / creaking audible → no forward
            into its bearing · oscillation breaker · model timeout → hold
                               │
                               ▼ WASD/look → Reactor
  BRAIN (onboard, offline): small vision + sound classifier taught by the cloud model (no network)
  SURVIVOR MODE: judge drives · Gemini Live guide hears the judge's mic + gets audio-sensor
                 hints · watchdog runs the same safety layer
  LEARNING: episode logs → judge → lessons playbook; logs → dataset → onboard + baseline models
```

**Three facts this design depends on:**
1. **Reactor generates video only, no sound.** All audio comes from our audio scene engine. The world model doesn't know where our sounds are, so when the agent reaches a sound source we **reveal** it with a prompt change ("a person trapped under a collapsed desk, waving").
2. **Direction comes from a simulated mic array, not the model.** AI models aren't reliable at telling where a sound came from in a recording. Our engine computes the bearing and distance (with realistic noise), the way a real robot's mic array would. ER 2 interprets *what* the sound is and decides *what to do*.
3. **Position is estimated from the robot's own moves.** The agent's position on the map (pose) is worked out by adding up its moves (dead reckoning). It's approximate, so use a few meters of tolerance when revealing sources and checking whether the agent arrived.

| Owns | FastAPI server, Gemini ER 2 agent, audio scene engine + mic array, safety layer, imagination scoring, scenario generator + traps, lessons playbook, Live API token minting, dataset + onboard model training, baseline + experiments | Next.js app, Reactor sessions, frame capture, HUD + audio radar, spatial audio playback, sound-source editor, imagination preview UI, survivor mode, data collection mode, offline mode, compare view, demo mode |
| Talks to | Gemini API (ER 2, TTS, Flash, image) | Reactor SDK, backend WebSocket, Gemini Live (via ephemeral token) |

**Why the frontend owns Reactor:** Reactor streams video, and that most likely runs in the browser. The browser therefore grabs frames from the video, sends them to the backend at about 2 fps, gets decisions back, and feeds the moves into Reactor. This design works whether or not Reactor has a Python SDK.

**Why the backend owns audio:** the backend knows the agent's estimated position and every sound source, so it can mix exactly what the robot "hears" without recording anything in the browser. The frontend plays the same sources through the room's speakers so the audience hears them too.

## Phase 3: Hearing (audio perception)

The agent hears what the camera can't see: a cry for help around a corner, tapping under rubble, gas hissing with no flame. It combines this with vision to decide. **This is your most reliable difference from a normal agent:** a vision-only agent *can't* find a survivor it can't see.

### P16 [A]: Audio scene engine + simulated mic array + hearing in the brain

```
In /backend/audio:
1. clips.py: build the clip library.
   - Voices via the Gemini TTS model: for each line, render 2-3 variants (different
     voices; style prompts like "weak and exhausted", "panicked shouting", "child
     crying", "calm news anchor" for decoys). Lines include: "Help! I'm stuck!",
     "Is anyone there?", "Don't come this way, the floor collapsed!", "My leg is
     trapped, please hurry", "Over here, by the stairs!", plus 2 non-English lines
     (e.g. Spanish, Hindi). Cache to static/audio/voices/ with a manifest (text, voice,
     style, language).
   - Effects: CC0 gas hiss, creaking/cracking, rushing water, fire crackle, fire alarm,
     knocking in an SOS rhythm, TV/radio chatter. Record sources in SOURCES.md.
2. engine.py: AudioScene(episode, scenario.audio_sources)
   - Each tick (~4 Hz), from the robot pose: bearing_deg + distance_m to every active
     source; gain = gain_db with distance falloff (inverse distance, clamp); muffled
     sources get a low-pass filter + an extra -8 dB.
   - Simulated mic array: estimated bearing = true + Gaussian noise (σ=12°,
     larger when muffled or far), distance estimate ±30%, and front/back confusion
     5% of the time (real mic arrays do this). Only sources above an audibility threshold
     are "heard".
   - mix_clip(seconds=2.5): mono 16 kHz mix of what the robot hears now (numpy), WAV bytes.
   - Emits {type:"audio_state"} to the frontend at ~4 Hz (true values, for speakers +
     radar).
   - Event detector: an audio event = a new source becomes audible, a voice starts or
     STOPS (silence after calling = urgency up), or loudness jumps.
   - Reveal: when pose is within reveal.radius_m of a source (and facing within ±40°),
     emit director_event kind:"reveal" with the reveal world_prompt. Mark the survivor
     found when the next frames confirm a person (ER 2) OR after 2 more steps of
     approach (tolerance for drifting pose).
3. Brain integration (agent/autopilot.py, when episode.hearing=true):
   - On an audio event, or every 4th decision while anything is audible, attach
     mix_clip() as audio input + a text block:
       "MIC ARRAY (estimates): src1 bearing -118° ±15°, ~7 m, muffled; src2 ..."
     (never send source ids, kinds, transcripts, or ground truth).
   - Extend the system prompt: use what you hear AND see. Voices = possible survivors,
     even when nothing is visible; muffled = behind a wall or under debris; a voice that
     goes silent raises urgency; spoken warnings ("floor collapsed") are hazard info for
     that direction; hiss/creak/rushing water = invisible hazards; TV/radio/echo =
     possible decoys (repeating, broadcast tone, no response to your movement).
     When survivors compete, prioritize by urgency, then reachable safely, then distance.
     Output heard[] with your interpretation and a one-line priority.
   - Mission state tracks heard sources (cluster by bearing and kind over time) so the
     agent can head toward a caller that has gone quiet.
4. Safety layer additions (deterministic):
   - Gas hiss or creaking audible within ±30° of the heading and estimated < 6 m -> no
     move W; turn away; override reason "invisible hazard ahead (audio)".
   - A spoken warning heard from a direction -> mark that bearing hazardous for 60 s.
5. POST /audio/trigger injects a source right now at a bearing/distance relative to the
   current pose (for the operator and the compare view).
6. Tests: bearing math, mic-array noise bounds, reveal trigger, safety audio rules.

STRETCH (onboard, P11): pretrained sound classifier (e.g. YAMNet) on the mixed clip ->
{voice, scream/cry, hiss, creak, water, alarm, knocking} + mic bearing -> simple rules
so the offline brain also reacts to sound.
```
**Done when:** in a calm corridor with a muffled "help" placed 120° to the left, the agent turns toward it, approaches, and the reveal fires. With hearing off, the same run walks straight past.

## Phase 4: Imagination ("look before you leap")

At a decision point, the agent grabs the current frame and starts 2–3 short Reactor sessions from it, one per option. It watches each imagined future, scores it, then commits to the best option in the real world.

### P5 [A]: Imagination orchestrator + scoring

```
In /backend implement agent/imagination.py.
When autopilot hits a decision point:
1. Build 2-3 options from the model's decision_point. For each option produce:
   - label ("Left doorway", "Stairs down", "Continue corridor")
   - world_prompt: the scenario prompt + a sentence steering the imagined continuation
     (e.g. "the camera moves through the left doorway into the next room")
   - drive: a short scripted action sequence (~3s total) that executes the option
2. Send {type:"imagine_request"} to frontend and PAUSE the autopilot for that episode.
3. On {type:"imagine_results"} (3-4 frames per option), call gemini-robotics-er-2-preview
   ONCE with all options' frames labeled, asking for JSON scores per option:
   risk 0-10, progress-toward-exit-or-survivors 0-10, one-sentence summary.
4. chosen = argmax(progress - 1.5*risk); ties -> lowest risk.
5. Send {type:"imagine_verdict"}, then resume autopilot with an injected first action
   that executes the chosen option's drive sequence.
6. Timeout: if no results in 15s, resume autopilot with the safest default and log it.
Record every imagination in the episode log (options, scores, chosen, and later whether
the real outcome matched, for the lessons system).
Also add a debug HTTP endpoint POST /debug/force_imagination/{episode_id} so the demo
operator can trigger it on cue.
```
**Done when:** a forced imagination returns sensible scores for real frames and autopilot resumes along the chosen path.

### P6 [B]: Imagination sessions + preview UI

```
In /frontend handle {type:"imagine_request"}:
1. Pause the main session's actions. Capture the current frame.
2. For each option IN PARALLEL: start a new ReactorSession with reference image = the
   captured frame, prompt = option.world_prompt; execute option.drive; capture a frame
   at ~1s intervals (3-4 frames); stop the session.
3. Send {type:"imagine_results"}.

FALLBACK (if P0-B showed concurrency is limited or session start is slow):

```

## Phase 7: Onboard model + "our agent vs a conventional agent" comparison

**The two claims we're testing (report the numbers honestly, whatever they turn out to be):**
1. **Hearing:** an agent that hears as well as sees makes the right call in the audio edge cases (hidden callers, invisible hazards, decoys, triage), where a vision-only agent can't.
2. **Imagination:** at trap scenarios, the same ER 2 agent avoids the trap more often *with* imagination than without.
3. **Endless worlds:** a model trained on *many* generated disasters handles **new disasters and real photos** better than the *same* model trained on one fixed map. The one-map model stands in for conventional simulator training, which uses a few hand-built environments.
4. **Onboard:** a small local model taught by the cloud model makes decisions about 50× faster and keeps working with no network.

Each claim changes **one thing at a time**, so each result shows the effect of one feature.

> **Fairness rules (judges will ask):** both students use the same architecture, the **same number of training frames**, the same safety layer, and are tested on worlds that **neither** saw during training. Split the data **by scenario, not by frame**. Frames from the same world appearing in both training and test would inflate the scores.

### P11 [A]: Dataset builder + onboard student model

```
In /backend/training:
1. build_dataset.py: turn episode logs into a dataset.
   Each example = frame JPEG + labels:
     move (W/A/S/D/none), hazard_ahead (any severity>=2 hazard with y>600 and
     300<x<700), exit_visible.
   Label source priority: safety-override action > ER 2 action. Survivor-mode episodes
   with outcome "escaped" add human demonstrations (tag source="human").
   Also store the 2.5 s audio clip + mic-array bearings when hearing was on (for the
   stretch onboard sound classifier).
   Exclude held_out scenarios (P4.5) entirely.
   Output: data/dataset/<scenario_id>/*.jpg + labels.csv + manifest.json (counts per
   scenario, class balance). Print a warning if any class < 5%.
2. train_student.py --scenarios all|<id> --max-frames N --out models/<name>.pt
   - Backbone: frozen pretrained DINOv2-small (or MobileNetV3 if speed matters more),
     features cached to disk on the first run so retraining takes seconds.
   - Head: small MLP with 3 outputs (move 5-way softmax, hazard_ahead sigmoid,
     exit_visible sigmoid). Weight hazard positives higher (missed hazards are the
     costly error).
   - Train on Apple Silicon via PyTorch MPS (fallback CPU). Validation split BY SCENARIO.
   - Save metrics + training curve to models/<name>.json.
3. agent/onboard.py: load a student model, run inference on a frame (<30ms target),
   return a decision in the contract format (source:"onboard", reason generated from a
   template, e.g. "Hazard ahead (0.91): backing off"). Points for HUD: none (student
   doesn't localize); the HUD shows a hazard confidence bar instead.
4. Wire agents: start_episode.agent selects cloud/onboard/baseline; set_agent switches
   mid-run; network_sim offline=true makes every cloud call fail fast so the episode
   auto-falls back to onboard and the decision reasons say so. Imagination is disabled
   while offline ("imagination needs the cloud; onboard reflexes only").
5. score.py (P4.5) supports --agent onboard --model <name>.
6. learning_curve.py: train the broad student on 250/500/1k/2k/all frames and
   score each on test_generated + test_real -> data/results/learning_curve.json.

STRETCH: onboard hearing (see P16 stretch): pretrained sound classifier + mic bearing +
rules, so in offline mode the robot still turns toward voices and away from hiss.
STRETCH (only if everything else is done): LoRA fine-tune a small open VLM (Gemma 3 or
PaliGemma) on the same data so the onboard model can give a short explanation too.
```

## Risk register

| Risk | Fallback |
|---|---|
| ER 2 doesn't understand audio well enough | Gemini Flash transcribes and classifies each clip, and ER 2 gets a text description (see P0-C) |
| Audio adds too much latency | Only send clips on audio events (P16); the safety audio rules react instantly without any model |
| Position estimate drifts, so the reveal fires in the wrong place or never | Bigger reveal radius; operator hotkey forces the reveal; recalibrate move speeds (P3) |
| Room speakers are mono or too quiet | The radar on the HUD carries the story; bring a small stereo speaker |
| Reactor concurrency or cost limits imagination | `IMAGINE_BACKEND=reactor_seq` or `image` (P6) |
| Only 1 Reactor session at a time, so no live side-by-side | Compare REPLAY mode from runs recorded one after another (P14) |
| ER 2 too slow for smooth motion | Decide every N frames, keep the previous move running, hide latency (P15) |
| Not enough diverse training frames | Start collection early (see Timeline); add hand-written prompts for more variety; the learning curve shows how much data was enough |
| ER 2 collection costs too much | Spending cap in collection mode (P12); collect at 1 fps |
| Onboard model is weak | Still show the latency + offline story; state its limits honestly |
| A comparison shows no difference | Report it; lead with the comparisons that do show one (hearing is the most likely). A judge will respect an honest result more than a suspicious one |
| Live voice is too slow or the room is loud | Push-to-talk plus captions, with the operator mic as backup |
| Venue Wi-Fi dies | Tether to a phone hotspot; backup videos (V hotkey) |
| Agent wanders aimlessly | Scenario prompts always include a visible exit sign; safety layer stops oscillation |
| Judge gets lost in survivor mode | Operator triggers `set_waypoint` / "Exit reached" by hotkey |
